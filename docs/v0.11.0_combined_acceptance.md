# ScoreForm v0.11.0 combined installed and physical acceptance

Issue: #195
Acceptance contract: `SF-AC15` plus the applicable `SF-AC01` through `SF-AC14` outcomes
Physical adjudicator: project owner

## Purpose

This document defines the candidate-level acceptance for the ScoreForm v0.11.0
teacher-workflow milestone. It deliberately separates two forms of evidence:

1. deterministic software acceptance from a clean noneditable ScoreForm wheel;
2. real printer/scanner acceptance performed and adjudicated by the project owner.

The automated layer proves that the v0.11 convenience features coexist in one
installed candidate and one synthetic workspace. It does not claim that paper was
printed, marks were visually correct, or a real scanner was used.

The physical layer supplements the automated layer. Automation must not claim a
physical pass.

Use synthetic identities only. Do not commit generated PDFs, filled sheets,
scans, result CSVs, retained-source files, diagnostic images, unrestricted
machine paths, or real student/classroom data.

## Automated combined installed acceptance

The canonical combined verifier is:

```text
scripts/verify_installed_v011_combined_acceptance.py
```

The isolated build/install runner is:

```text
scripts/run_v011_combined_wheel_acceptance.py
```

The verifier is intentionally not a wrapper around the focused #183–#194
acceptance scripts. It exercises production ScoreForm/Core services in one
shared installed workspace so cross-feature identity and lifecycle transitions
are observable.

The scenario covers:

- source assignment reuse through both assignment copy and non-student preset;
- bulk answer-key/alignment preview, atomic validation, and apply;
- one multi-class generation plan across copied and preset-applied targets;
- fresh issuance/page/route identity across generated physical copies;
- recent/active assignment continuity;
- successful retained PDS2 scan-to-results continuation;
- duplicate-content attempt idempotency;
- a deterministic missing-page failure and later complete recovery;
- readiness `ready=True` while unresolved attention exists;
- privacy-conscious diagnostic event persistence;
- first guided publication;
- legitimate successor manifest and exact supersession;
- installed `scoreform = scoreform.cli:main` launcher ownership;
- direct CLI preservation;
- absence of Meridian and `paper-data-suite` runtime dependencies;
- no unqualified legacy assignment work path.

The combined verifier filters semantic records by identity and cardinality. It
must not select "the first" class, assignment, issuance, provider, route, or
publication merely because an operating system or metadata API returned it
first.

### Local isolated-wheel qualification

Use the exact released Core 0.6.3 wheel:

```powershell
$Work = Join-Path $env:TEMP (
    "scoreform-v011-combined-" + [guid]::NewGuid().ToString("N")
)

python .\scripts\run_v011_combined_wheel_acceptance.py `
  --repository . `
  --work $Work `
  --core-wheel "$HOME\Downloads\pds_core-0.6.3-py3-none-any.whl" `
  --expected-core-version 0.6.3
```

The runner:

- stages the current working tree outside the checkout;
- builds one wheel and one source distribution;
- validates release-artifact contents;
- authenticates the exact Core 0.6.3 wheel identity and SHA-256;
- creates a fresh venv;
- installs Core and ScoreForm noneditably;
- runs `pip check`;
- executes the combined verifier from outside the source tree.

`PYTHONPATH`, `PYTHONHOME`, and user-site imports are excluded from trusted
execution.

The dedicated Core 0.6.2/0.6.3 module-operations qualification from #194 remains
separate and must continue to pass. #195 does not replace the Core compatibility
floor test.

## Physical fixture

Use three synthetic classes in the acceptance workspace:

- one source/reuse class;
- one copied target;
- one preset-applied target.

Use one synthetic student in each target to keep physical identity and expected
artifact counts mechanically auditable.

For the real paper run, retain a standard two-page assignment:

```text
layout: standard_15q_abcd_v1
question count: 30
physical pages per issuance: 2
choices: A/B/C/D
```

The source key may repeat A/B/C/D. The copied target may be bulk-edited as the
automated combined scenario does.

## Physical step 1 — reuse and multi-class generation

Run the installed teacher-facing ScoreForm workflow, not an editable checkout.

Confirm the teacher can:

1. select/reuse the source assignment;
2. create the copied target without inherited result/scan/publication history;
3. apply a reusable setup preset to the other target;
4. review/apply the intended bulk key/alignment;
5. select both target class/assignment pairs in one multi-class generation plan.

Before committing generation, verify the plan identifies both semantic targets
and expected student/output counts.

Cancel one rehearsal plan and confirm no generation state is created.

Then run the generation.

Machine-check before printing:

- both selected target assignments still exist and are byte-valid;
- each target has one class packet and one individual PDF for its one student;
- every physical copy has a fresh issuance;
- every page has a fresh page ID;
- every routed page has a fresh Core route ID;
- no issuance/page/route identity is reused across the two targets;
- logical pages are exactly 1 and 2 for the selected two-page issuance;
- no unqualified `classes/<class>/assignments/` work tree exists.

Select the physical candidate by class/assignment/output/issuance identity, not
by directory enumeration position.

## Physical step 2 — print and visually inspect

Print at actual size/100%. Do not use "fit to page".

Visually inspect every page used in the paper test:

- class/assignment header;
- question labels;
- answer boxes;
- QR placement and legibility;
- all four registration marks;
- clipping or printer scaling;
- page ordering;
- overall practical teacher usability.

Record printer settings that can materially change geometry.

## Physical step 3 — successful retained scan

Use one fresh issuance from the copied target.

Mark this deterministic pattern:

- Q5: intentionally incorrect;
- Q20: intentionally incorrect;
- Q30: blank;
- every other question: keyed answer.

Expected score: `27/30`.

Scan both pages together with the intended classroom scanner/imaging workflow.
Record orientation, auto-rotation, deskew/enhancement, duplex/simplex behavior,
and resolution where relevant.

Process the scan through the installed guided **Process Scans** / retained PDS2
workflow. Do not substitute `decode-qr` for the teacher-facing path.

Pass conditions:

- both physical QR codes decode;
- all registration marks are usable;
- Core retains the selected source;
- both pages resolve to the exact printed issuance;
- page/route/logical/source provenance is aligned;
- the result is schema-v2 `pds2_scan`;
- the result score is exactly `27/30`;
- the guided workflow offers the exact result target;
- reviewing the just-produced result does not require manual class/assignment
  reselection;
- ScoreForm does not designate the attempt official/best/latest.

Then deliberately process identical successful scan bytes again. Confirm the
attempt is already present and no new attempt row is appended. Another retained
intake may legitimately exist as separate evidence.

## Physical step 4 — first guided publication

Keep the successful copied target as active/recent context.

Run **Share Results with Meridian**.

Verify the guided journey creates or resolves the separate architecture records:

1. Academic Work Registration;
2. immutable ScoreForm manifest revision;
3. Core Publication Record/catalog state.

The teacher should not need to reacquire the same class/assignment merely to
bridge those stages.

Record only sanitized publication status. ScoreForm must not import Meridian
runtime code.

## Physical step 5 — missing-page failure

Use a second fresh physical issuance. Do not reuse the successful issuance.

Mark the complete paper with a known answer pattern, but initially scan/process
only page 1 of the two-page issuance.

Required behavior:

- Core retains the partial source;
- no complete ScoreForm attempt/result row is created;
- the review classification is missing/incomplete page evidence;
- teacher guidance states that the evidence is retained;
- teacher guidance recommends locating/rescanning the missing page rather than
  forcing an incomplete attempt;
- a cancelled non-manual action is labelled according to the actual action.

The project owner must judge the guidance while physically holding the paper.
This is a usability observation that software-only automation cannot make.

Record the supported `rescan_needed` resolution or equivalent approved recovery
action. Confirm the original failure bytes/evidence are not rewritten.

## Physical step 6 — complete rescan recovery

Scan/process the complete two-page second issuance.

Verify:

- both pages dispatch to the same exact second issuance;
- recovery produces one legitimate complete result;
- the original missing-page failure remains in immutable/append-only history;
- the rescan resolution remains recorded;
- no route/page identity is borrowed from the first successful issuance.

## Physical step 7 — successor publication

The second legitimate native result provides successor producer evidence.

Run **Share Results with Meridian** again.

Verify:

- the current exact publication is resolved from canonical Core state;
- a new immutable producer revision is created;
- the teacher sees the current and proposed successor state;
- exact supersession confirmation is required;
- the expected current Core head is superseded;
- the previous publication remains in immutable history;
- the successor becomes current;
- no publication is inferred from filesystem order or retyped opaque IDs when
  canonical state can resolve them safely.

## Physical step 8 — diagnostics and readiness/attention

With the recovered failure history still present, inspect the normal
teacher-facing diagnostics.

Confirm the default view is useful without exposing prohibited synthetic
privacy sentinels, answer payloads, result rows, raw scans, or unnecessary
absolute paths.

Deep technical details may remain available through the approved debug policy.

Also verify ScoreForm remains operationally ready for the valid workspace/class
while legitimate attention can still exist. Attention must not redefine
readiness.

Suite exact-version qualification remains Suite-owned. The released Paper Data
Suite v0.1.0 exact-qualifies ScoreForm 0.10.0 and must not be altered by this
ScoreForm issue to pretend an unreleased candidate is exact-compatible.

## Failure handling

If any physical step fails:

1. do not mark the physical gate passed;
2. preserve the sanitized failure observation;
3. add the narrowest deterministic regression test possible;
4. correct the product/acceptance code in a reviewed branch;
5. build a new clean candidate;
6. rerun the authoritative automated qualification;
7. repeat the physical procedure required by the candidate-invalidation rule.

#196 performs the final usability/privacy/compatibility/release audit after this
combined installed and physical acceptance is complete.
