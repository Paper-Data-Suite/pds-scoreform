Issue: #182  
Milestone: v0.11.0 — Teacher Workflow Efficiency and Troubleshooting

Baseline commit: `047e47f60730b8a5540b5e1d92f008ffad37eede`

Declared Core compatibility: `pds-core>=0.6,<0.7`

## Purpose

This document records the pre-v0.11.0 teacher workflow so later usability work can be judged against a stable baseline rather than recollection. It is deliberately a workflow audit, not a proposal to move authority between repositories or collapse exact records for convenience.

The baseline is the exact `v0.10.0` release commit from which branch `182-audit-teacher-journey-acceptance-cases` was created. The branch contained no v0.11.0 implementation changes when the audit began.

The audit uses synthetic teacher/class/assignment scenarios only. No real student information, scans, results, school documents, or private workspace paths are part of the evidence.

## Evidence method

The counts below are deterministic control-flow measurements of the teacher-facing functions at the baseline commit. The audit traced the actual prompt, menu, confirmation, cancellation, and return paths in:

- `scoreform/cli.py`

- `scoreform/menu_navigation.py`
- supporting workflow and result-view code where needed
- the existing tests covering publication cancellation, generation-output menus, scan review, roster editing, navigation, result viewing, and release/physical acceptance

These are workflow counts, not wall-clock timing measurements or a human-subject usability study. A teacher action means one menu selection, value entry, confirmation, path/record entry, or blocking continue/back response. A screen means a distinct rendered teacher-facing task view or header instance. A pause counts as an action when the teacher must press Enter to continue, but not as a separate screen unless the program redraws a new view.

The exact installed Core micro-version is intentionally not baked into this historical source baseline because ScoreForm declares the compatible `0.6.x` range. Installed qualification must record the exact Core and Python versions used when #195 runs.

Physical printing, marking, scanning, and visual paper inspection are not claimed here. Those observations remain project-owner physical acceptance in #195. Existing v0.10.0 physical-acceptance documentation was reviewed only to identify the current intended teacher path and physical cases that must remain covered.

## Current menu inventory

### Main Menu

The current main menu contains four teacher-facing areas:

1. Assignment Management
2. Roster Management
3. Workspace Settings
4. Help

### Assignment Management

Assignment Management is a flat twelve-item menu:

1. Create an assignment
2. Edit an assignment
3. Validate an assignment file
4. Generate answer sheets
5. Score scanned responses
6. View assignment results
7. Decode QR from a file
8. Enter Plain-Paper Results
9. Resolve scan review items
10. Academic Work Registration
11. Academic Result Manifests
12. Academic Result Publications

The menu mixes ordinary teacher tasks, low-level validation/diagnostic operations, recovery operations, and three separate publication lifecycle surfaces at one level.

### Generation

The teacher generation submenu has two entry points:

1. generate answer sheets for one existing class assignment;
2. generate a generic blank template.

The existing-class path selects one class, then one assignment, then confirms generation. After success it can open the class packet or individual-sheet folder.

The noninteractive `scoreform generate` path is more capable in one important respect: it accepts one assignment file plus multiple roster files. That is useful implementation leverage for later multi-class work, but it is not exposed as a teacher planning workflow for already-managed assignments.

### Scan scoring

Interactive scoring first selects a file from `scans_inbox` or accepts a custom path, then asks the teacher to choose retained PDS2 Core dispatch or manual answer-key scoring. The recommended PDS2 path derives class/assignment/student identity from retained routing rather than asking the teacher to select the assignment.

After routed scoring completes, the workflow pauses and returns to Assignment Management. It does not carry the resolved assignment directly into result review.

### Scan review

Scan review lists unresolved/deferred items, opens a detailed record, then offers actions according to the failure and available identity. The detail view may expose route ID, page ID, issuance ID, raw payload, retained source, resolution history, and diagnostic identity in addition to teacher-relevant failure information.

The workflow correctly preserves append-only resolution semantics and requires explicit `WRITE` confirmation before writing a resolution. A UI defect is present in the cancellation path: when `_perform_action()` returns no result, the enclosing menu always renders the heading `Manual Entry Cancelled`, even when the cancelled action was, for example, `rescan_needed`, `defer`, or a route action. The body accurately says no result or resolution was written, but the heading is misleading. This belongs with later scan/recovery usability work rather than being fixed opportunistically in #182.

### Plain-paper entry

Plain-paper entry selects class and assignment once and then keeps that context while the teacher enters multiple students. This is an existing positive pattern: after one result is written, the teacher returns to the student list for the same class and assignment rather than reacquiring both identities.

### Academic publication

Academic publication currently requires three distinct menu entries:

- Academic Work Registration
- Academic Result Manifests
- Academic Result Publications

Each entry independently discovers classes, asks for class, discovers assignments, and asks for assignment. The workflows then expose the exact state required by their underlying contracts: registration intent/lifecycle and revision, manifest revision, producer-head revision, publication ID, and exact supersession/withdrawal confirmations where applicable.

The exactness is an integrity property; the repeated acquisition and fragmented teacher journey are usability problems.

### Concrete creation counts

For the shortest create path that skips standards:

- 10 questions: 19 actions;
- 25 questions: 34 actions.

For a simple standards case that chooses one profile and attaches one selected standard to a comma-separated question set:

- 10 questions: 24 actions;
- 25 questions: 39 actions.

The dominant term is the answer key: creation requires exactly one answer prompt per question. There is no paste/CSV/JSON bulk-entry preview in the teacher workflow.

The Save Assignment screen shows assignment identity and selected classes, but it does not present a complete answer-key/alignment preview followed by a commit confirmation. New files are written after validation; overwrite prompts occur only where a target already exists.

### Concrete answer-key edit counts

The edit workflow changes one answer at a time. For `K` corrections, the shortest path from Main Menu through save is:

```text
8 + 3K actions
```

Examples:

- 1 corrected answer: 11 actions;
- 5 corrected answers: 23 actions;
- 25 corrected answers: 83 actions.

The edit summary intentionally truncates a long answer key, so it is not a complete bulk verification surface for a large change.

Standards editing is somewhat better: one action can attach selected standards to a comma-separated set of questions. That capability should be preserved or reused rather than replaced with per-question-only alignment.

### Concrete repeated-generation count

Generating one existing assignment for two classes through the menu requires two separate passes through the generation submenu:

```text
Main Menu
  -> Assignment Management
  -> Generate Answer Sheets
  -> existing class assignment
  -> class 1
  -> assignment
  -> confirm
  -> post-generation action
  -> Assignment Management
  -> Generate Answer Sheets
  -> existing class assignment
  -> class 2
  -> assignment
  -> confirm
  -> post-generation action
```

That shortest two-class path is 13 teacher actions. There is no combined preview of intended packets/sheets before starting the batch.

The direct CLI already accepts multiple rosters for one assignment definition, so #186 should examine reuse of exact generation services rather than inventing a second generation owner.

### Concrete scan-to-results count

The recommended routed scan path itself does not require manual class/assignment selection:

```text
Assignment Management
  -> Score scanned responses
  -> choose from scans_inbox
  -> choose scan
  -> retained PDS2 Core page dispatch
  -> process/pause
```

But result review is a separate workflow:

```text
Assignment Management
  -> View assignment results
  -> select class
  -> select assignment
  -> review/pause
```

Together, the shortest successful path from Assignment Management back to Assignment Management is 9 teacher actions and 10 rendered task/header instances. The principal usability issue is not that routed scoring lacks identity; it has already resolved identity. The issue is that this context is discarded before review.

### Concrete first-publication count

A normal first publication currently requires:

```text
Main Menu
  -> Assignment Management
  -> Academic Work Registration
     -> select class
     -> select assignment
     -> register action
     -> academic intent
     -> lifecycle
     -> REGISTER
  -> Assignment Management
  -> Academic Result Manifests
     -> select class
     -> select assignment
     -> generate
     -> GENERATE
  -> Assignment Management
  -> Academic Result Publications
     -> select class
     -> select assignment
     -> publish producer head
     -> producer head revision
     -> PUBLISH
```

Shortest successful count: **19 teacher actions**.

The same class is selected three times and the same assignment is selected three times. This is the clearest baseline for #191: the underlying registration, immutable manifest, and Core publication records must remain distinct, but the teacher should not have to reconstruct the relationship between them manually.

### Concrete supersession count

With a legitimate successor native state already available, generating a successor manifest and superseding the exact current publication requires two independent class/assignment acquisitions. From Main Menu, the shortest path is 13 actions, including explicit successor revision, expected current publication ID, and `SUPERSEDE` confirmation.

Revision and publication identity are not themselves defects. Exact head matching is a concurrency/integrity requirement. #191 should reduce mechanical lookup/re-entry while still making the exact current and proposed successor states reviewable before confirmation.

## Cancellation audit

### Assignment creation

Cancellation is uneven after class selection.

- Class selection supports shared Back/Main/Quit navigation.
- A blank title is treated as an error and exits the creation attempt rather than a named cancel path.
- Assignment-ID entry has no explicit cancel after title selection.
- Layout and question-count prompts have no shared navigation handling.
- Answer-key entry loops until an A–D answer is entered for every question; there is no normal cancel command inside the loop.
- Standards selection again supports navigation.
- No assignment is written until the later save phase, so these gaps are primarily workflow friction rather than observed partial-write defects.

Later work should provide a consistent way to abandon uncommitted setup without requiring a keyboard interrupt or deliberately invalid input.

### Assignment editing

Assignment edits are staged in memory. Leaving with dirty state requires exact `DISCARD`; saving requires exact `SAVE`. Historical results are not silently rescored when the answer key is edited. This is a good integrity pattern to preserve.

### Generation

Class/assignment selectors support shared navigation. The final `Generate answer sheets now? (Y/n)` prompt supports an ordinary `n/no` cancellation before generation begins. Post-generation opening is optional.

### Scan scoring

The scan source and scoring-mode selectors support shared navigation. Manual answer-key scoring requires an answer-key path and can return without running if it is absent.

### Scan review

Review-list and action selection support shared navigation. Resolution writes require exact `WRITE`. Manual entry adds another exact `WRITE` before the manual result is accepted.

Observed UI inconsistency: a cancelled non-manual review action is reported under the heading `Manual Entry Cancelled`. No durable state is implied by that heading, but it misidentifies the operation and should be corrected by #189/#190.

### Academic Work Registration

Class/assignment selection, intent/lifecycle choice, and explicit cancel/return paths all permit exit before writing. `REGISTER`/`UPDATE` confirmations guard mutation.

### Manifest generation

Class/assignment selection can be cancelled. Generation requires exact `GENERATE`. Existing code distinguishes partial-success cases where a revision is already durably allocated, so later guided UI must not simplify away that recovery distinction.

### Publication

Publication, supersession, republication, withdrawal, and catalog rebuild use exact confirmation tokens. Existing menu tests explicitly verify wrong or blank confirmations do not run the guarded mutation. Later convenience work must preserve that behavior or an equivalent explicit commit boundary.

## Failure and recovery audit

### Routed scan failures

Core retention and ScoreForm review records already provide a safe evidence boundary. The usability problem is the amount and level of information a teacher must interpret after failure.

The scan-review detail screen can expose:

- failure category and message;
- source filename/page;
- class/assignment/student identity;
- route ID;
- page ID;
- issuance ID;
- logical page;
- observed diagnostic identity;
- retained source path;
- raw payload;
- validated route/target;
- resolution history.

Those fields are valuable for exact recovery and diagnostics, but they compete with the teacher's immediate question: **what should I do next with this paper?** #190 should keep exact evidence available while presenting actionable teacher guidance first.

### Incomplete/duplicate/conflicting attempts

Current scoring/attempt assembly correctly refuses to export incomplete, duplicate-conflicting, mixed-issuance, or otherwise invalid attempt sets. This is an integrity invariant, not workflow friction to remove. A guided flow may summarize the condition and lead into review, but it must not write a result merely to avoid a recovery step.

### Publication partial success

Manifest/publication code already distinguishes failures after durable state may exist and tells the caller to inspect/reload canonical state before retrying. #191 must preserve that recovery semantics. A single guided workflow must not turn an uncertain durable write into an automatic retry.

## Mapping to v0.11.0 work

### #183 — Assignment copying

Use `SF-U02`, `SF-F04`, and the existing class-qualified managed-work layout as the baseline. Copying must reduce configuration re-entry while creating a new class-qualified assignment context and fresh issuance/route/result history.

### #184 — Reusable setup presets

Use the repeated non-student configuration identified in `SF-U01`/`SF-U02`. Presets should reuse layout/question-count/key-structure/alignment plan without becoming mutable prior assignments or copying student evidence.

### #185 — Fast answer-key and alignment entry/import

Use the `N + 9`, `N + 14`, and `8 + 3K` measurements as the primary baseline. Preserve grouped standards attachment while adding validated bulk entry and a complete preview/commit boundary.

### #186 — Multi-class generation planning

Use the 13-action two-class generation case. Reuse existing exact generation services and fresh identity creation. Planning should preview all selected work and isolate failures without reusing issuance/page/route identities.

### #187 — Task-oriented Assignment Management

Use the twelve-peer-option inventory plus cancellation findings. Ordinary teacher tasks should be discoverable without deleting advanced exact commands.

### #188 — Recent/continue-work context

Use `SF-F01`, `SF-U05`, `SF-U06`, `SF-U09`, and `SF-U10`. Context must be visible and clearable and must not become a separate student-data cache outside the workspace.

### #189 — Guided scan-to-results

Use the 9-action successful score-to-review path and the post-failure transition into scan review. The guided path should carry resolved context and preserve direct/manual modes.

### #190 — Scan-quality diagnostics

Use the dense scan-review detail inventory and `SF-F10`. Teacher guidance should identify what happened and the safe next action before exposing deep route/issuance diagnostics.

### #191 — Share Results with Meridian

Use the 19-action first-publication and 13-action successor/supersession baselines. The guided workflow should retain one assignment context while preserving separate registration, manifest, Core publication, exact-head, and recovery semantics.

### #192 — Privacy-conscious diagnostics

Use `SF-F16` plus the repository's existing rule that generated/scanned/result material is potentially sensitive. Default diagnostics must not reproduce student answers, raw results, or uncontrolled absolute paths.

### #193 — Attention and next-action summaries

Use the unresolved-scan, incomplete-attempt, publication-state, and recent-context findings above to define concise ScoreForm-owned attention summaries. Expose only bounded module state through the shared provider contract; do not move scoring or publication authority into the suite shell.

### #194 — Suite doctor and launcher integration

Use the environment/dependency observations and task-oriented menu findings as the ScoreForm baseline for bounded readiness/version/dependency reporting and stable launcher entry points. The suite shell may discover readiness and launch ScoreForm, but it must not become a scoring, attempt-selection, or publication owner.

### #195 — Installed and physical acceptance

Re-run representative acceptance cases from the clean installed wheel and perform the real print/scan workflow. Record exact Python/Core/ScoreForm versions and physical observations there.

### #196 — Final audit

Compare the completed milestone against `docs/v0.11.0_usability_acceptance_cases.md`, this baseline, privacy rules, Core authority, direct CLI compatibility, and release artifacts.

## Physical observations deferred to #195

- whether real scanner output produces the expected successful and failed paths;
- whether rescan guidance is understandable when holding the physical paper;

## Audit conclusion

The v0.10.0 workflow is structurally safe but mechanically fragmented. The strongest existing properties are exact PDS2 identity, retained evidence, staged edits, explicit publication mutation boundaries, and a direct CLI that exposes deterministic operations. The largest teacher-workload costs are repeated answer-key setup, inability to copy an existing assessment into a later class, one-assignment-at-a-time generation, loss of class/assignment context between tasks, separation of successful scoring from result review, and a three-surface publication sequence.

v0.11.0 should therefore add guided workflows **over** the existing exact services. It should not trade provenance, attempt preservation, Core authority, publication exactness, or recovery semantics for fewer prompts.
