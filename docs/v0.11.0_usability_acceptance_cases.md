# ScoreForm v0.11.0 usability acceptance cases

Issue: #182  
Baseline: ScoreForm `0.10.0` at `047e47f60730b8a5540b5e1d92f008ffad37eede`  
Companion baseline: `docs/v0.11.0_teacher_workflow_audit.md`

## Purpose

These cases define the observable teacher-workflow outcomes expected from ScoreForm v0.11.0. They are acceptance contracts for later milestone issues, not a requirement to preserve the v0.10.0 menu implementation.

Each case distinguishes teacher convenience from data/authority invariants. A later implementation may change menu structure, prompts, helper functions, or internal composition while still satisfying the case.

## Classification

Each case is tagged with one or more validation modes:

- **automatable** — behavior can be covered with synthetic unit/integration tests;
- **installed** — must be exercised from a clean noneditable wheel installation;
- **physical** — requires real printing/scanning or project-owner visual/physical confirmation and is deferred to #195.

Physical validation supplements rather than replaces automatable integrity checks.

## `SF-AC01` — Task-oriented Assignment Management

**Owner:** #187  
**Modes:** automatable, installed

### Preconditions

ScoreForm has a valid workspace with at least one class and assignment.

### Teacher goal

Find the ordinary next action without distinguishing a dozen peer-level implementation operations.

### Required observable outcome

The teacher-facing Assignment Management surface groups or guides common tasks around recognizable goals such as:

- create/copy/setup;
- print/generate;
- process scans;
- review results;
- plain-paper entry;
- share results.

Advanced validation, QR decoding, low-level publication operations, and other exact recovery commands remain reachable but do not need to compete as equal peers with the common daily workflow.

### Invariants

- No direct CLI command is removed solely because a guided menu exists.
- Menu grouping does not move scoring, publication, routing, or grading authority.
- Back/Main/Quit behavior remains deterministic.

### Cancellation/recovery

Leaving a grouping screen before a selected operation starts creates no new domain state.

## `SF-AC02` — Copy an assignment into another class safely

**Owner:** #183  
**Modes:** automatable, installed

### Preconditions

A source class contains a valid managed ScoreForm assignment. A different target class has a valid roster.

### Teacher goal

Reuse the source assignment's teacher-selected configuration without re-entering the full setup.

### Required observable outcome

The teacher can select source assignment and target class(es), review the proposed copy, adjust the copyable fields, and create target assignments without retyping the entire answer key and alignment.

The copied assignment receives the correct class-qualified managed identity. No result/evidence history is copied.

### Invariants

Copying must not copy or reuse:

- result rows or attempts;
- generated sheet artifacts;
- issuance IDs;
- page IDs;
- route IDs;
- retained scans;
- scan-review records/resolutions;
- manifest revisions;
- publication records.

Layout/question-count/answer-key/standards configuration may be copied only according to the #183 contract and after teacher review.

### Cancellation/recovery

Cancelling before commit creates no target assignment. A conflict with one target must be reported explicitly and must not fabricate identity reuse to make the copy succeed.

## `SF-AC03` — Reusable non-student setup preset

**Owner:** #184  
**Modes:** automatable, installed

### Preconditions

At least one reusable preset exists or the teacher is creating one from permitted non-student configuration.

### Teacher goal

Start a new assessment from a known setup without treating an old assignment as a mutable template.

### Required observable outcome

The teacher can apply reusable non-student configuration such as layout, question count, answer-key structure, and alignment plan, then review/edit it before creating the new assignment.

### Invariants

- Presets contain no roster, student, response, score, attempt, scan, issuance, route, manifest, or publication data.
- Editing a preset does not mutate prior assignments.
- Applying a preset creates a normal new assignment through ScoreForm-owned validation/storage.

## `SF-AC04` — Fast answer-key and alignment entry with atomic preview

**Owner:** #185  
**Modes:** automatable, installed

### Preconditions

The teacher is creating or editing an assignment with a known question count and choice set.

### Teacher goal

Enter or replace a substantial key/alignment without one prompt per question.

### Required observable outcome

A teacher can use a concise paste or supported CSV/JSON input for the key/alignment. Before any assignment mutation, ScoreForm shows a complete normalized preview or equivalent complete validation summary and reports all detected validation problems.

The teacher is not required to perform `N` separate answer prompts when a valid bulk form is available.

### Invariants

- Question numbers must be in range and complete according to the operation contract.
- Answers must belong to the assignment choice set.
- Standard IDs must resolve through the selected Core standards profile.
- One invalid item must not leave a partially applied key/alignment.
- Existing per-question editing may remain as an advanced/fine-grained path.

### Cancellation/recovery

Cancel at preview leaves the assignment unchanged. Validation failure leaves the assignment unchanged and returns actionable field/question diagnostics.

## `SF-AC05` — Multi-class generation planning

**Owner:** #186  
**Modes:** automatable, installed, physical

### Preconditions

At least two compatible managed assignments/classes are available for generation.

### Teacher goal

Prepare all intended packets/sheets in one planning session.

### Required observable outcome

The teacher can select multiple compatible class/assignment targets, see what will be generated, and start generation without re-entering the generation submenu once per target.

The preview identifies expected classes, assignments, student counts, output kinds, and any target that cannot proceed.

### Invariants

- Every target uses existing exact generation services.
- Every new physical copy receives fresh issuance/page/route identity according to current contracts.
- A failure in one target does not cause identity reuse or silent corruption in another.
- Completed targets and failed targets are reported separately.

### Cancellation/recovery

Cancel before generation writes no new generation state. Partial batch completion must truthfully report durable successes and the failed target; retry must not duplicate a completed copy by accident.

### Physical gate

#195 must verify representative generated output and real print/scan behavior from the installed candidate.

## `SF-AC06` — Recent and active assignment context

**Owner:** #188  
**Modes:** automatable, installed

### Preconditions

The teacher has just completed or entered a workflow for one class/assignment.

### Teacher goal

Continue working with the same assignment without repeatedly finding it again.

### Required observable outcome

Where safe and relevant, ScoreForm offers or retains the recent class/assignment context and displays it prominently. The teacher can change or clear it explicitly.

During one continuous guided task, a known class/assignment should be selected **at most once** unless the teacher deliberately switches context.

### Invariants

- Recent context is a convenience reference, not a second canonical assignment record.
- It must not persist student result/response payloads outside their authoritative workspace records.
- Stale/missing context must fail closed and return to normal selection rather than guessing.

## `SF-AC07` — Guided retained scan to result review

**Owner:** #189  
**Modes:** automatable, installed, physical

### Preconditions

A supported PDS2 scan is available and resolves to a ScoreForm target.

### Teacher goal

Process the scan and inspect the resulting assignment outcome as one task.

### Required observable outcome

After successful retained PDS2 dispatch/attempt assembly, the teacher can proceed directly to the relevant result/attempt summary without manually reselecting class and assignment.

After route resolution, the guided path requires **zero manual class/assignment reselections** merely to review the result just produced.

### Invariants

- Core retains source bytes before dispatch.
- ScoreForm uses validated registered target identity.
- Complete-attempt and idempotency rules remain unchanged.
- The result view does not choose an official/best/latest attempt.
- Manual and direct CLI scoring modes remain available.

### Cancellation/recovery

Leaving after scoring does not delete retained evidence or results already durably written. If scoring fails, the flow transitions to an actionable unresolved/review state rather than manufacturing a result.

### Physical gate

#195 must verify the same path with actual printed/scanned synthetic paper.

## `SF-AC08` — Actionable scan-quality recovery

**Owner:** #190  
**Modes:** automatable, installed, physical

### Preconditions

A retained scan produces a known failure such as registration/alignment, QR/route, duplicate/conflict, incomplete attempt, ambiguity, or mixed assignment/issuance.

### Teacher goal

Understand the problem and choose the next safe action.

### Required observable outcome

The primary teacher view states:

1. what failed in teacher-meaningful language;
2. whether evidence is safely retained;
3. the recommended next action, such as rescan, resolve identity, defer, or use an appropriate manual fallback.

Deep route/page/issuance/raw-payload diagnostics may remain available but should not be required reading for ordinary recovery.

A cancelled non-manual action must be labelled according to the operation actually cancelled; it must not report `Manual Entry Cancelled` for unrelated actions.

### Invariants

- Failure records and resolution history remain immutable/append-only according to Core/ScoreForm contracts.
- Incomplete or conflicting attempts do not become result rows.
- Manual fallback cannot fabricate routed provenance.

### Physical gate

#195 should confirm that rescan guidance is usable with real synthetic paper/scanner failures.


### Implementation evidence

Implemented by #190 with focused source tests plus clean installed-wheel
`SF-AC08` acceptance. Automated coverage exercises teacher-first diagnostics,
retained-evidence wording, registration/alignment classification, QR-less
recovery, missing-page and conflicting-duplicate guidance, exact
`source_scan_id` scoping, technical-details separation, truthful non-manual
cancellation, privacy boundaries, and preservation of direct scan-review CLI
surfaces.

Automated acceptance does not establish printer/scanner usability; physical
confirmation remains open for #195.

## `SF-AC09` — Consistent safe cancellation

**Owners:** #185, #187, #189, #191  
**Modes:** automatable, installed

### Preconditions

The teacher is inside an uncommitted create/edit/generate/scan/publication step.

### Teacher goal

Abandon or back out of the current step without guessing whether state was written.

### Required observable outcome

Every guided workflow has a documented and discoverable cancellation path before its commit point. The UI clearly distinguishes:

- no durable state written;
- durable state already written and only the remaining step cancelled;
- partial-success/recovery state that must be inspected before retry.

Assignment creation must not require deliberately invalid input or a keyboard interrupt merely to abandon uncommitted title/ID/layout/question/key entry.

### Invariants

- Existing staged assignment/roster edit semantics remain safe.
- Exact mutation confirmation may be retained where it protects important state.
- Cancellation must never delete retained scan evidence or immutable history.

## `SF-AC10` — One guided first-publication journey

**Owner:** #191  
**Modes:** automatable, installed

### Preconditions

A managed ScoreForm assignment has valid results and is not yet registered/published.

### Teacher goal

Share the producer evidence through the supported Core publication architecture without manually orchestrating three independent menus.

### Required observable outcome

`Share Results with Meridian` or the agreed teacher-facing equivalent carries one selected assignment through:

1. registration readiness and registration if needed;
2. manifest readiness/generation;
3. publication readiness;
4. first publication;
5. final status.

Within one continuous guided run, class is selected **at most once** and assignment is selected **at most once** unless the teacher changes context.

The UI explains the outcome in teacher terms while still allowing the exact registration/manifest/publication state to be inspected.

### Invariants

- The workflow still writes separate Core Academic Work Registration and Publication Records and ScoreForm immutable manifest revisions.
- ScoreForm does not import or depend on Meridian implementation code merely because the teacher-facing action says `Share Results with Meridian`.
- Publication does not calculate proficiency or Grade and does not select an official attempt.
- Existing advanced registration/manifest/publication commands remain available.

### Cancellation/recovery

Cancel before a specific commit prevents that commit. If an earlier stage has already become durable, later cancellation must report that durable state rather than claiming the whole workflow was rolled back.

## `SF-AC11` — Exact successor publication and supersession

**Owner:** #191  
**Modes:** automatable, installed

### Preconditions

A publication series has a current Core head and ScoreForm has legitimate successor native evidence.

### Teacher goal

Publish the successor without manually copying opaque IDs when ScoreForm can safely resolve them.

### Required observable outcome

The guided workflow shows the current exact publication/head and proposed successor manifest/revision, then requests explicit supersession confirmation.

The teacher should not need to rediscover the same class/assignment in separate menus. Opaque revision/publication identity may be shown for exactness but should be resolved from canonical state where safe rather than retyped solely as mechanical glue.

### Invariants

- Supersession is conditional on the exact expected current Core head.
- Immutable producer revisions remain immutable.
- A stale-head conflict fails safely and requires state reload/review.
- Withdrawal/republication semantics remain exact.

### Cancellation/recovery

A conflict or partial success must report durable canonical state and the safe next action. Automatic blind retry is prohibited.

## `SF-AC12` — Preserve deterministic direct CLI surfaces

**Owners:** #187–#191  
**Modes:** automatable, installed

### Preconditions

The installed package exposes its documented direct commands.

### Teacher/developer goal

Use exact noninteractive commands for diagnostics, scripting, development, and recovery even after menus become simpler.

### Required observable outcome

Existing supported direct operations remain prompt-free where they are prompt-free in v0.10.0 and continue to expose deterministic exit status/output contracts unless a separately documented compatibility change is approved.

At minimum preserve the roles of direct:

- generation/regeneration;
- scoring;
- scan-review listing/resolution;
- Academic Work Registration;
- manifest operations;
- publication operations;
- workspace/school-year/scan-filing commands.

### Invariants

Guided menus call or compose exact application services; they do not become the only implementation of critical business behavior.

## `SF-AC13` — Privacy-conscious context and diagnostics

**Owners:** #188, #190, #192  
**Modes:** automatable, installed

### Preconditions

Recent-context, scan-diagnostic, logging, or troubleshooting behavior is enabled.

### Teacher goal

Receive useful continuity and diagnostics without creating another uncontrolled store of student information.

### Required observable outcome

Default context/diagnostic records use the minimum identifiers needed for the feature and do not reproduce answer payloads, result rows, roster details, raw grades, or unrestricted absolute paths.

Deep debug artifacts require the explicit policy/opt-in defined by #192 and remain within approved workspace boundaries.

### Invariants

- No real student data appears in repository fixtures/tests/docs.
- Retained scans/results remain in their authoritative workspace locations.
- Logs/troubleshooting bundles follow the milestone's prohibited-field rules.

## `SF-AC14` — Preserve ScoreForm/Core/Meridian authority boundaries

**Owners:** all v0.11.0 issues; final verification #196  
**Modes:** automatable, installed

### Preconditions

Any new v0.11.0 convenience workflow is exercised.

### Teacher goal

Gain speed without changing the meaning of evidence or Grades.

### Required observable outcome

All convenience paths preserve these boundaries:

- Core owns shared workspace, routing/retention, Academic Work Registration, Publication Records/catalogs, and shared registry authority.
- ScoreForm owns assessment definition, sheet generation, scoring, exact attempt evidence, result manifests, and producer-side publication operations.
- ScoreForm preserves legitimate attempts and does not choose the official/best/latest attempt.
- Meridian owns attempt-selection policy, proficiency interpretation, and Grade policy.

### Prohibited outcomes

No v0.11.0 workflow may:

- calculate a course Grade in ScoreForm;
- calculate Meridian proficiency policy in ScoreForm;
- silently choose one attempt as official;
- reuse issuance/page/route identity during assignment copying;
- bypass Core retention/route validation for routed scans;
- mutate immutable manifest/publication history for convenience.

## `SF-AC15` — Installed and physical end-to-end qualification

**Owner:** #195  
**Modes:** installed, physical

### Preconditions

All implementation issues required for the v0.11.0 candidate are merged and a clean candidate wheel is available.

### Teacher goal

Verify that the convenience improvements work in the environment where ScoreForm is actually used.

### Required observable outcome

From a clean noneditable installation, synthetic acceptance covers at least:

- copied/reused assignment setup;
- multi-class generation;
- real print/scan scoring;
- successful scan-to-results review;
- failed-scan recovery;
- first publication and successor publication;
- direct CLI availability;
- privacy-conscious diagnostics;
- no regression to PDS2 attempt/provenance behavior.

Record exact:

- candidate commit/tree;
- wheel hash;
- Python version;
- Core version;
- ScoreForm version;
- relevant external prerequisites.

Physical observations remain project-owner adjudicated and cannot be claimed by an automated agent.

## Final milestone use

#196 should treat these cases as a checklist of outcomes, not implementation snapshots. If later work changes a case intentionally, update the case and explain why rather than silently accepting a regression.

The v0.11.0 milestone is successful only if teacher workload is reduced **without** weakening exact attempt preservation, PDS2 routing/retention, immutable publication history, privacy boundaries, or Core/Meridian ownership.
